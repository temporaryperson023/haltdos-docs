Webhook Testing Guide

Haltdos · Testing  ·  Last updated May 2026  ·  10 min read

This guide walks through the complete process of setting up, triggering, and verifying webhooks on the Haltdos platform using webhook.site as a free live receiver — no prior knowledge required.

How It Works

Before diving in, here's the full picture of what we're doing:

🛡 Haltdos Platform
— Event occurs (attack, alert, traffic spike)
↓
Webhook fires — sends HTTP POST request
🌐 webhook.site
— Receives and displays the request live
↓
👀 You
— Verify method, headers, and payload

💡 webhook.site is a free tool that gives you a unique URL. Any HTTP request sent to that URL appears on the page in real time — perfect for testing without writing any code.

Understanding Webhooks

A webhook is an automatic HTTP request that Haltdos fires when something happens on the platform — like a security event, traffic spike, or alert. Instead of you checking the dashboard manually, Haltdos pushes the information to any URL you configure.

The configuration fields you'll encounter:

Field What it does Tester's Note
Enable Turns the webhook on or off Always test both enabled and disabled states
Name Label for this webhook Test with special characters, long strings, and blank
Stack Which stack this webhook is scoped to Test with valid and invalid stacks
HTTP Method POST / PUT / DELETE / UPDATE POST is default — test all four methods
URL The endpoint that receives the payload Your webhook.site URL goes here
Payload Location Where data is sent — ARG, PARAM, or BODY Critical — changes how payload is delivered
Payload Name The key name for the payload Test blank and special characters
Attribute Type ARG / PARAM / HEADER / COOKIE For passing auth tokens or custom metadata
Attribute Name Name of the attribute e.g. Authorization, x-api-key
Attribute Value Value of the attribute e.g. your token value

Understanding Payload Location

This is the most important field to understand as a tester. It controls where the data lands in the HTTP request:

Option Where data is sent Example
BODY Inside the request body — standard for REST APIs {"testPayload": "value"}
PARAM As a query parameter appended to the URL ?testPayload=value
ARG Passed as an argument — similar to query args URL argument format

⚠️ Make sure your receiver is checking the correct location based on what you configure. A mismatch means the payload arrives but you won't find it where you're looking.

Step-by-Step Testing

1

Get Your Free Receiver URL from webhook.site

Open a new browser tab and go to:

https://webhook.site

The moment the page loads, you will see a unique URL at the top that looks like this:

webhook.site — Your unique URL
https://webhook.site/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx

Copy that URL — this is your personal temporary receiver. Every HTTP request sent to this URL will appear live on the left panel of this page.

⚠️ Keep this tab open the entire time. If you refresh the page you will get a new URL and lose visibility of previous requests.

2

Create a Webhook in Haltdos

Log in to your Haltdos Enterprise dashboard and navigate to:

🗂 System › Integration › Webhooks

Click Add Webhook and fill in the form with these exact values:

Field Value to enter
Enable Enabled
Name Test-Webhook-1
Stack Select your stack from the dropdown
HTTP Method POST
URL ← Paste your webhook.site URL here
Payload Location BODY
Payload Name testPayload
Attribute Type HEADER
Attribute Name x-test-header
Attribute Value haltdos-test-123

Click Save Changes.

💡 What we just did — we told Haltdos: "When an event fires, send a POST request to my webhook.site URL, put the data in the request body, and attach a custom header called x-test-header so I can verify it arrived."

3

Trigger the Webhook

For the webhook to fire, an event must occur on the Haltdos platform. As a tester you have two options:

  • Wait for a real event — a traffic spike, security alert, or system event will automatically trigger configured webhooks
  • Manually trigger a test event — check under System → Events to see if your setup supports manually firing a test event

💡 Some Haltdos versions have a "Send Test" or "Test Webhook" button directly on the webhook configuration page. Check if yours does — it's the easiest way to trigger it immediately.

4

Watch It Arrive on webhook.site

Switch back to your webhook.site browser tab. On the left panel a new entry will appear — this is the incoming request from Haltdos. Click on it and you will see the full request details:

webhook.site — Incoming Request
Method: POST URL: /xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx   Headers: x-test-header: haltdos-test-123   Body: { "testPayload": "..." }

✅ If you see this — it worked! Haltdos successfully fired a webhook and your receiver captured it.

5

Verify Everything — Your Checklist

Once the request arrives on webhook.site, go through each of these verification points one by one:

Check What to look for Expected Result
✅ Method Look at the Method field at the top Should be POST
✅ URL Check the URL the request hit Should match your webhook.site unique path
✅ Custom Header Look in the Headers section x-test-header: haltdos-test-123 present
✅ Payload Look in the Body section testPayload key present with a value
✅ Payload Location Confirm data is in BODY not URL params Since we set BODY — data should not be in the URL

Troubleshooting — Nothing Arrived?

If nothing shows up on webhook.site after triggering an event, work through this checklist:

Symptom Likely Cause Fix
No request on webhook.site Webhook is disabled Go back to the webhook config and confirm Enable is turned on
No request on webhook.site Wrong URL pasted Copy the webhook.site URL again — make sure there are no extra spaces
No request on webhook.site No event triggered Confirm an actual event fired on Haltdos — check System → Events
No request on webhook.site Outbound network blocked Ask your admin if the Haltdos server can make outbound HTTP calls
Request arrives but payload missing Wrong Payload Location Check BODY vs PARAM — make sure you're looking in the right place
Request arrives but header missing Attribute not saved correctly Re-check Attribute Name and Value fields in the webhook config

Advanced Test Scenarios

Once the basic test passes, run through these scenarios to do a thorough verification:

Functional Tests

# Test How to test Expected
F1 HTTP Method — POST Set method to POST, trigger event webhook.site shows POST
F2 HTTP Method — PUT Change method to PUT, trigger event webhook.site shows PUT
F3 Payload Location — BODY Set to BODY, check request body on webhook.site Payload in request body as JSON
F4 Payload Location — PARAM Set to PARAM, check URL on webhook.site Payload as ?testPayload=value in URL
F5 Custom header sent Check Headers section on webhook.site x-test-header: haltdos-test-123

Negative Tests

# Test How to test Expected
N1 Invalid URL Enter a non-existent URL, trigger event Haltdos handles failure gracefully — no crash
N2 Disabled webhook Disable the webhook, trigger event Nothing arrives on webhook.site
N3 Blank payload name Leave Payload Name empty, save and trigger Either validation error or empty key in payload
N4 Unreachable URL Enter https://localhost:9999, trigger event Haltdos should log a delivery failure

Edge Case Tests

# Test What to check
E1 Duplicate webhook names Create two webhooks with the same name — does Haltdos allow it?
E2 Multiple webhooks for same stack Do all webhooks fire? Does order matter?
E3 Very long attribute value Enter 500+ character value — does it get truncated?
E4 Special characters in name Use !@#$%^&*() in the Name field — validation behavior?
