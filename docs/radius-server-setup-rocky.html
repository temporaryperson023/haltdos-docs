RADIUS Server Setup on Rocky Linux

Haltdos · Configuration  ·  Rocky Linux / RHEL  ·  Last updated June 2026  ·  10 min read

This guide walks through setting up a FreeRADIUS authentication server on Rocky Linux using Docker Compose. By the end you will have a running FreeRADIUS container with live log monitoring, users configured, and the Haltdos platform authenticated against it.

⚠️ All commands in this guide must be run as root or with sudo. The user home directory used throughout is /home/haltdos — replace this with your actual username if different.

Prerequisites

  • Rocky Linux VM (or RHEL / CentOS equivalent) — this guide uses IP 172.16.0.17
  • Internet access on the VM to pull Docker packages and the FreeRADIUS image
  • A user account — this guide uses haltdos as the username
  • The Haltdos platform installed and reachable on the same network

Step 1 — Install Docker

Add the Docker CE repository and install Docker along with the Compose plugin:

sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker

Verify Docker is running:

docker --version
sudo systemctl status docker

💡 docker-compose-plugin is the modern replacement for the standalone docker-compose binary. All compose commands in this guide use docker compose (with a space, not a hyphen).

Step 2 — Create the Project Structure

Create the working directory under the haltdos home folder:

mkdir -p /home/haltdos/freeradius-docker/config
cd /home/haltdos/freeradius-docker

⚠️ Important path note: Always create and run from /home/haltdos/freeradius-docker/. Do NOT work inside /root — if you accidentally create files there, move them with mv /root/freeradius-docker /home/haltdos/freeradius-docker and fix ownership with chown -R haltdos:haltdos /home/haltdos/freeradius-docker.

Step 3 — Create the Configuration Files

clients.conf

This file defines which IP addresses are allowed to send authentication requests to the RADIUS server. You must include an entry for every client — the container itself, Docker's internal network, your VM network, and the Haltdos platform IP.

cat > /home/haltdos/freeradius-docker/config/clients.conf << 'EOF'
client localhost {
    ipaddr          = 127.0.0.1
    secret          = radius123
    nastype         = other
    require_message_authenticator = false
}

client docker_internal {
    ipaddr          = 172.18.0.0/16
    secret          = radius123
    nastype         = other
    require_message_authenticator = false
}

client rocky_network {
    ipaddr          = 172.16.0.0/24
    secret          = radius123
    shortname       = rocky-radius
    nastype         = other
    require_message_authenticator = false
}

client haltdos_platform {
    ipaddr          = 10.0.0.160         # <- add the actual Haltdos platform IP here
    secret          = radius123
    shortname       = haltdos
    nastype         = other
    require_message_authenticator = false
}
EOF

⚠️ Unknown client errors: If you see Ignoring request … from unknown client <IP> in the logs, that IP is missing from clients.conf. Add a new client block for it and restart the container.

users

This file defines the usernames and passwords FreeRADIUS will authenticate against:

cat > /home/haltdos/freeradius-docker/config/users << 'EOF'
radadmin    Cleartext-Password := "Test#123"
            Reply-Message = "Login OK, %{User-Name}"

kartik      Cleartext-Password := "Kartik#123"
            Reply-Message = "Login OK, %{User-Name}"
EOF

Config Fields Explained

Field Value Description
ipaddr IP or CIDR The client IP or subnet allowed to send RADIUS requests. Use CIDR notation like 172.16.0.0/24 to allow a whole subnet.
secret radius123 Shared secret between the RADIUS server and the client. Must match exactly on both sides.
nastype other Type of NAS device. Use other for generic clients like Haltdos.
Cleartext-Password Password string Plaintext password stored in the users file. FreeRADIUS compares this against the password sent by the client.
Reply-Message String with %{User-Name} Message returned to the client on successful authentication. The %{User-Name} macro is replaced with the actual username.

Step 4 — Create the Docker Compose File

cat > /home/haltdos/freeradius-docker/docker-compose.yml << 'EOF'
services:
  freeradius:
    image: freeradius/freeradius-server:latest
    container_name: freeradius
    restart: unless-stopped
    ports:
      - "1812:1812/udp"
      - "1813:1813/udp"
    volumes:
      - ./config/clients.conf:/etc/raddb/clients.conf
      - ./config/users:/etc/raddb/users
    command: freeradius -X
    networks:
      - radius-net

networks:
  radius-net:
    driver: bridge
EOF

The key settings in this file:

Setting Value Description
1812:1812/udp Port mapping RADIUS authentication port. UDP is required — TCP will not work.
1813:1813/udp Port mapping RADIUS accounting port.
./config/clients.conf:/etc/raddb/clients.conf Volume mount Mounts your clients file into the container, overriding the default.
./config/users:/etc/raddb/users Volume mount Mounts your users file into the container.
freeradius -X Command Runs FreeRADIUS in debug mode so all activity appears in docker logs.
restart: unless-stopped Restart policy Container restarts automatically on reboot or crash unless you manually stop it.

Step 5 — Open Firewall Ports

RADIUS uses UDP ports 1812 (auth) and 1813 (accounting). Open both permanently:

sudo firewall-cmd --permanent --add-port=1812/udp
sudo firewall-cmd --permanent --add-port=1813/udp
sudo firewall-cmd --reload

All three commands should return success. If you see ALREADY_ENABLED warnings that is fine — the ports are already open.

Step 6 — Start the Container

cd /home/haltdos/freeradius-docker
sudo docker compose up -d
sudo docker ps

You should see output like this:

bash — root@localhost
root@localhost:~# sudo docker ps 200cb69d5644 freeradius/freeradius-server:latest "/docker-entrypoint.…" 1 second ago Up Less than a second 0.0.0.0:1812-1813->1812-1813/udp freeradius

Step 7 — Test Authentication Locally

Run radtest from inside the container to verify both users authenticate correctly:

sudo docker exec -it freeradius radtest radadmin "Test#123" 127.0.0.1 0 radius123
sudo docker exec -it freeradius radtest kartik "Kartik#123" 127.0.0.1 0 radius123

A successful response looks like this:

bash — root@localhost
Sent Access-Request Id 0 from 0.0.0.0:53509 to 127.0.0.1:1812 length 78 User-Name = "radadmin" User-Password = <<< secret >>> Received Access-Accept Id 0 from 127.0.0.1:1812 to 127.0.0.1:53509 length 58 Reply-Message = "Login OK, radadmin"

✅ Access-Accept means authentication succeeded. If you see Access-Reject or No reply from server, see the Troubleshooting section below.

Step 8 — View Live Authentication Logs

Since FreeRADIUS runs in debug mode (-X), all output goes to stdout and is accessible via Docker logs. This is the equivalent of tail -f for this setup:

sudo docker logs -f freeradius

When a user authenticates successfully from the Haltdos platform you will see entries like this:

bash — root@localhost — docker logs freeradius
(0) Received Access-Request Id 4 from 10.0.0.160:38217 to 172.18.0.2:1812 length 65 (0) User-Name = "kartik" (0) chap: CHAP user "kartik" authenticated successfully (0) Sent Access-Accept Id 4 from 172.18.0.2:1812 to 10.0.0.160:38217 length 56 (0) Reply-Message = "Login OK, kartik"

To view logs from inside the container file system directly:

sudo docker exec -it freeradius tail -f /var/log/freeradius/radius.log

Troubleshooting

No reply from server

The most common cause is a missing client entry. The container's internal IP (172.18.0.x) must be in clients.conf. Make sure the docker_internal block covers 172.18.0.0/16, then restart: 

sudo docker compose restart

Ignoring request from unknown client <IP>

That IP is not in clients.conf. Add a new client block for it, save the file, and restart the container. Common missing IPs are the Haltdos platform address (10.0.0.160 in this setup) or a new VM on the network.

BlastRADIUS warnings

You may see warnings like:

FreeRADIUS warning
The packet does not contain Message-Authenticator, which is a security issue. UPGRADE CLIENT haltdos AS YOUR NETWORK MAY BE VULNERABLE TO THE BLASTRADIUS ATTACK.

These warnings appear because the Haltdos platform sends CHAP authentication requests without the Message-Authenticator attribute. In a controlled test environment this is acceptable. The authentication still succeeds — you will see Access-Accept in the same log output. For production deployments, upgrade the RADIUS client on the Haltdos side to include Message-Authenticator.

Access-Reject on correct credentials

Check that the password in the Haltdos RADIUS configuration matches exactly what is in the users file — including case. Also check that the shared secret in clients.conf matches the secret configured on the Haltdos platform side.

Day-to-Day Operations

Task Command
Check if container is running sudo docker ps | grep freeradius
View live logs sudo docker logs -f freeradius
Add or edit a user vi /home/haltdos/freeradius-docker/config/users
Add or edit a client IP vi /home/haltdos/freeradius-docker/config/clients.conf
Apply config changes sudo docker compose restart from the project folder
Stop the container sudo docker compose down
Start the container sudo docker compose up -d
Test a user from inside the container sudo docker exec -it freeradius radtest <user> "<password>" 127.0.0.1 0 radius123

⚠️ Always run commands from inside /home/haltdos/freeradius-docker/ so Docker Compose can find the docker-compose.yml file. After editing clients.conf or users, always run sudo docker compose restart to apply the changes.
