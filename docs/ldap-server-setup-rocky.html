LDAP Server Setup on Rocky Linux

Haltdos · Configuration  ·  Rocky Linux 9  ·  Last updated June 2026  ·  12 min read

This guide walks through setting up a 389 Directory Server (LDAP) on Rocky Linux 9 and configuring the Haltdos platform to authenticate users against it. By the end you will have a running LDAP server with a test user that can log into Haltdos.

Architecture

⚠️ All commands in this guide run on the Rocky Linux VM (172.16.0.18) unless stated otherwise. Run as root or with sudo. Replace IPs with your actual values if different.

Prerequisites

  • Rocky Linux 9 VM — this guide uses IP 172.16.0.18
  • Haltdos platform running — this guide uses IP 10.0.0.160
  • Both VMs can reach each other on the network
  • Root or sudo access on the Rocky Linux VM

💡 Why 389 Directory Server? The standard openldap-servers package was removed from Rocky Linux 9 default repos. 389 DS is the Red Hat-maintained replacement — it's fully supported, available by default, and has no extra repo needed.

Step 1 — Install 389 Directory Server

Install directly from the default Rocky Linux 9 AppStream repo — no extra repositories needed: 

dnf install -y 389-ds-base

When complete you should see Complete! at the bottom of the output.

Step 2 — Create the Directory Server Instance

389 DS uses an interactive setup tool called dscreate. Run it and answer each prompt as shown below:

dscreate interactive

Answer each prompt exactly like this:

Prompt What to enter Notes
Enter system's hostname Press Enter Accept default — localhost.localdomain
Enter the instance name Press Enter Accept default — localhost
Enter port number Press Enter Accept default — 389
Create self-signed certificate database Press Enter Accept default — yes
Enter secure port number Press Enter Accept default — 636
Enter Directory Manager DN Press Enter Accept default — cn=Directory Manager
Enter the Directory Manager password Test#123 This is your admin password — remember it
Confirm the Directory Manager password Test#123 —
Choose whether mdb or bdb is used Press Enter Accept default — bdb
Enter the database suffix Press Enter Accept default — dc=localhost,dc=localdomain
Create sample entries in the suffix yes Type yes — creates the ou=People structure automatically
Do you want to start the instance after the installation? Press Enter Accept default — yes
Are you ready to install? yes Type yes to begin

When complete you will see:

bash — root@localhost
Starting installation ... Validate installation settings ... Create file system structures ... Create self-signed certificate database ... Perform SELinux labeling ... Create database backend: dc=localhost,dc=localdomain ... Perform post-installation tasks ... Completed installation for instance: slapd-localhost

Step 3 — Verify the Service is Running

systemctl status dirsrv@localhost

You should see Active: active (running) and these key lines confirming both ports are open:

bash — root@localhost
Active: active (running) Status: "slapd started: Ready to process requests" Listening on All Interfaces port 389 for LDAP requests Listening on All Interfaces port 636 for LDAPS requests

Press q to exit the status view.

✅ Both port 389 (LDAP) and port 636 (LDAPS) are listening on all interfaces — the server is ready.

Step 4 — Add a Test User

Create a user LDIF file and add it to the directory:

cat > /tmp/testuser.ldif << 'EOF'
dn: uid=testuser,ou=People,dc=localhost,dc=localdomain
objectClass: inetOrgPerson
objectClass: organizationalPerson
objectClass: person
objectClass: top
cn: Test User
sn: User
uid: testuser
userPassword: Test#123
EOF
ldapadd -x -D "cn=Directory Manager" -w "Test#123" -H ldap://localhost -f /tmp/testuser.ldif

Expected output:

bash — root@localhost
adding new entry "uid=testuser,ou=People,dc=localhost,dc=localdomain"

Verify the user was added correctly:

ldapsearch -x -D "cn=Directory Manager" -w "Test#123" -H ldap://localhost -b "dc=localhost,dc=localdomain" "(uid=testuser)"

You should see numEntries: 1 and the user details returned.

Step 5 — Fix Read Permissions (ACI)

By default 389 DS restricts directory searches to admin only. Without this step, Haltdos will connect but fail to find the user. Add a read ACI that allows authenticated users to search the directory:

ldapmodify -x -D "cn=Directory Manager" -w "Test#123" -H ldap://localhost << 'EOF'
dn: dc=localhost,dc=localdomain
changetype: modify
add: aci
aci: (targetattr="*")(version 3.0; acl "Allow all read"; allow (read,search,compare) userdn="ldap:///anyone";)
EOF

Expected output: modifying entry "dc=localhost,dc=localdomain"

🚨 This is the most critical step. Without this ACI, Haltdos will show authentication failed / Invalid user in its logs even though the LDAP server is reachable and the user exists. The connection succeeds but the search returns 0 entries because the user has no permission to read their own entry.

Step 6 — Open the Firewall

firewall-cmd --permanent --add-service=ldap
firewall-cmd --reload
firewall-cmd --list-services

Verify ldap appears in the listed services output:

bash — root@localhost
success success cockpit dhcpv6-client ldap ssh

Step 7 — Verify Connectivity from Haltdos

Run these commands from the Haltdos machine (10.0.0.160) to confirm it can reach and search the LDAP server.

First install ldap clients on the Haltdos machine if not already present:

dnf install -y openldap-clients

Then verify the connection:

curl -v ldap://172.16.0.18:389

Then verify the user is searchable as themselves — this simulates exactly what Haltdos does during login:

ldapsearch -x -H ldap://172.16.0.18 \
  -D "uid=testuser,ou=People,dc=localhost,dc=localdomain" \
  -w "Test#123" \
  -b "ou=People,dc=localhost,dc=localdomain" \
  "(uid=testuser)"

You must see numEntries: 1 — if you see numEntries: 0 go back and repeat Step 5.

✅ numEntries: 1 means the LDAP server is reachable, the user exists, and the permissions are correct. Haltdos will now be able to authenticate this user.

Step 8 — Configure LDAP in Haltdos UI

Log into the Haltdos dashboard and navigate to:

🗂 System › Integration › LDAP

Fill in the configuration fields exactly as shown:

Field Value Notes
Enabled Enabled Turn the toggle on
Endpoint ldap://172.16.0.18 IP of your Rocky Linux LDAP VM
Domain localhost.localdomain Matches the suffix set during dscreate
RootDN ou=People,dc=localhost,dc=localdomain The OU where users live — do NOT use AD-style CN=Users
User ID Attribute uid Matches the attribute used in the user LDIF
User Object Class inetOrgPerson Matches the objectClass used in the user LDIF
Group Member Attribute member Use member not memberOf — 389 DS uses groupOfNames style

Click Save Changes.

⚠️ RootDN is not the admin DN. It is the search base — where Haltdos looks for users. Setting it to cn=admin,dc=... will cause login to fail. It must be ou=People,dc=localhost,dc=localdomain.

Step 9 — Test the Login

Log out from the current Haltdos session, then log in with:

Field Value
Username testuser
Password Test#123

✅ If login succeeds — your LDAP integration is fully working end-to-end.

Troubleshooting

Symptom in Haltdos Logs Cause Fix
authentication failed / Invalid user — no LDAP connection attempt visible Haltdos config is wrong — not even reaching the LDAP server Check the Endpoint URL, Domain, and RootDN fields in the Haltdos LDAP config
Search returns numEntries: 0 when searching as testuser ACI not applied — user has no permission to read directory Repeat Step 5 — apply the ACI on the LDAP server
curl: Connection refused on port 389 Firewall blocking port 389 Repeat Step 6 — open the ldap firewall service
Search works from LDAP VM but not from Haltdos machine 389 DS only bound to localhost, not external interface Run ss -tlnp | grep 389 — should show *:389 not 127.0.0.1:389
Login fails even after ACI fix Wrong RootDN in Haltdos UI RootDN must be ou=People,dc=localhost,dc=localdomain — not the admin DN
